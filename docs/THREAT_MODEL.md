# Threat model

Fabric protects developers from **accidents and mistakes** — by agents, tools and people —
on a machine they control. It is not a sandbox and does not defend against a deliberately
malicious agent running with the user's privileges.

## Assets

1. The user's project files, especially uncommitted work.
2. Stored snapshots and the record of agent actions.
3. The correctness of what Fabric reports (a false "restored and verified" is a failure).

## Threats and status

| Threat | Mitigation | Status |
|---|---|---|
| Interrupted write (crash, kill, power loss) exposes a partial object | temp file + fsync + atomic rename; stale temps removed on open | implemented; real-kill test pending |
| On-disk corruption or tampering returns wrong content | every read verifies header, length and BLAKE3 | implemented, tested |
| Missing object treated as empty | distinct `Missing` error | implemented, tested |
| Two processes write the same store | exclusive OS file lock | implemented, tested |
| Store created inside / over a user directory | `init` refuses non-empty foreign directories | implemented, tested |
| Agent or tool overwrites stored objects | objects read-only; store outside project root | partial — read-only implemented; deliberate deletion is out of scope |
| Restore overwrites user work | snapshot-before-restore (undo point), conflicts for any uncaptured file it would touch, re-check that nothing changed since planning | implemented, tested |
| Restore with corrupt or missing stored content | missing refused at planning; every file staged and verified before the project is touched | implemented, tested |
| Interrupted restore leaves a half-restored project | journal + idempotent operations + resume; tested with a simulated crash before every operation | implemented; real-kill test pending |
| Restore reported as successful but wrong | post-restore snapshot compared entry by entry with the target | implemented, tested |
| Malicious paths in a manifest (`..`, absolute, `\`, `:`) | validated on construction and on every load | implemented, tested |
| Reserved Windows names (`CON`, `NUL`), case collisions on restore | reported as conflicts when planning | implemented, tested |
| Symlinks escaping the project during capture | symlinks recorded, never followed | implemented, tested |
| Symlinks escaping the project during restore | every parent is checked to be a real directory before each operation | implemented; no dedicated race test yet |
| Secrets captured in snapshots or logs | default exclusions (`.env*`, `*.pem`, `*.key`, SSH keys); no environment dumps | implemented for snapshots, tested |
| Verification runs untrusted project scripts | only explicitly configured commands; never during restore | planned |
| Agent runs destructive Fabric commands (`restore`, `revert`, `guard set`) | guard denies them for hooked agents; MCP exposes no destructive tools | implemented for Claude Code, tested |
| Agent deletes files, rewrites Git history, drops data, destroys infrastructure or publishes without consent | guard asks the person first (pattern-based, not a sandbox); checkpoints make in-project damage undoable | implemented for Claude Code, tested; other agents: undo only |
| Agent disables its own guard (edits hooks, Fabric data, `.git`) | writes to agent config ask; writes to Fabric data and `.git` are denied; policy lives outside the project | implemented, tested |
| Agent approves its own held change | `fabric approve` denied by the guard; refused where a known agent marks its shell (`CLAUDECODE`, `CODEX_SANDBOX`); approval bound to the exact action's digest and used once | implemented, tested; not proof against an agent deliberately evading both, nor against the prompting developer approving (recorded: approver, OS account, same-account flag) unless signed approvals are required |
| The developer approves or reviews their own agent's change | with `fabric approver require on`, approvals and reviews must be signed by a registered approver's key from another Fabric installation, checked against the exact actions or content; signatures re-verified offline from the evidence | implemented, tested; shows that the holder of a registered key decided, not who holds it; someone with write access to Fabric's data directory can register their own key (the registration is recorded) |
| Controlled file changed without approval (e.g. by a shell command the guard cannot attribute to a path) | after every agent step, changed files are checked against `approve`/`deny` rules and that step's approvals; unapproved controlled files are rolled back at once (content kept in the step's checkpoint) and anything that cannot be rolled back is an evidence exception | implemented, tested; the change exists on disk between the command and the rollback, so a process reading the file in that window can see it |
| A change authorization used beyond what was reviewed | a change covers one agent session and its path globs only, never held shell commands or `deny` rules; review binds the decision to the exact state shown (re-captured before recording) and closes the change | implemented, tested; while a change is open, its paths are controlled by the later review, not by per-edit approval, so a change rejected at review must still be reverted by a person |
| Agent posts to the books or moves money through a tool (MCP) without approval | rules over `server/tool` names; the Claude Code hook and `fabric mcp-proxy` hold matching calls for a recorded approval, deny destructive ones, and record every call with arguments and result; the proxy fails closed if the rules cannot be read | implemented, tested; matches tool names only, not arguments; a tool reached other than through the hook or the proxy is not controlled; calls are recorded, not undone |
| A delegated mandate used beyond its terms | limits checked under a lock before each covered call (tool, agent, per call, per day, count, expiry, revocation); every use recorded and replayed against the terms by `evidence verify` and `verify-pack`; signed grants when the project requires them | implemented, tested; a mandate naming an agent requires the agent's token (see below), one without an agent covers any caller; amounts are read from arguments by name (`amount`, `debit`), so a tool that moves money under another argument name is covered only by a mandate without amount limits |
| An agent obtains the credentials of the systems it acts on | credentials stored outside every project and given only to the upstream server's environment; injected values scrubbed from server responses before the agent or the evidence sees them; agents denied the credential commands and any tool call or command naming the store | implemented, tested; a server that transforms a credential (encodes, truncates) before echoing it is not caught; values under 8 characters are not scrubbed; an agent with shell access as the same OS user can still read files it can find, which the guard checks by path only |
| A gateway purchase decision changed or hidden after the fact (`cosigna-agent`) | every budget, agent grant, task step and reservation change is appended to a hash-chained `evidence` table in the same transaction (append-only triggers); `cosigna-agent evidence verify` re-hashes the chain and checks current budgets, tasks, reservations and agents against their last record | implemented, tested (ledger v4); detects edited, removed or reordered records and state changed outside the service, not a consistent rewrite of the whole chain by someone with database write access (no signing or anchoring yet); state from before v4 is listed as unevidenced |
| A payment with an unknown outcome is released while it can still succeed, or held forever (`cosigna-agent`) | unknown results stay held; only the owner's `resolve` can settle them, and only through the provider: an accepted attempt returns its receipt, otherwise the provider records a tombstone that refuses any late copy of the request before the hold is released; the Stripe test merchant retrieves the PaymentIntent or repeats the original idempotent create and cancels it | implemented, tested with the fixture provider, the HTTP test merchant and a fake Stripe; depends on the provider honouring the tombstone and on Stripe's 24-hour idempotency window (after it the attempt stays held); not tested against live Stripe |
| An agent refunds or pays out more than it should, twice, or without authority (`cosigna-agent` money operations) | the rail checks every request against its own records before any decision (payment exists, refundable amount, registered payee, currency) and again at execution; policy denies anything outside the agent's grant, the per-operation limit or the remaining budget, auto-approves only up to the agent's limit and holds the rest for the owner's exact-digest approval; holds share the purchase budget; one attempt per approval; denials are recorded | implemented, tested on the synthetic fixture rail; no live rail is connected yet; the agent's grant is checked, but who the payee really is (a changed bank account, a new payee) is not yet probed (planned, #89) |
| The Stripe key leaks to an agent or elsewhere, or a refund is duplicated or misreported (`stripe_test` rail) | the key is read by the gateway process only, never printed, recorded or returned; only test keys are accepted; requests go only to api.stripe.com (a loopback override exists for tests); each refund uses an idempotency key from its single attempt and is accepted only after retrieving it and matching amount, currency, PaymentIntent and metadata; pending, rate-limited and failed calls stay unknown and held | implemented, tested against a local fake of the Stripe API (idempotency, over-refund refusal, lost responses, dropped requests, pending); run once by hand against a real Stripe test account (`scripts/stripe-test-check.mjs`, 26 October 2026); resolve completes an approved refund within Stripe's 24-hour key window and leaves it held after |
| A self-hosted gateway is reached around its TLS proxy, over plain HTTP, or under another host name (`serve --listen --public-host`, `deploy/docker`) | with a public host set, every request except the health check must name that host and carry `X-Forwarded-Proto: https`; a non-loopback listen address without a public host is refused at startup; in Compose only the proxy publishes ports and the gateway runs unprivileged on a read-only filesystem | implemented, tested (`tests/self_host.rs`) and checked once with Docker Compose; the forwarded header is trusted, so the gateway port must stay unreachable except from the proxy |
| An agent impersonates another to use its mandate or scopes | per-agent tokens issued by a person, stored as hashes, authenticated by the proxy before it starts; mandates naming an agent cover only authenticated calls; tokens never forwarded upstream | implemented, tested; a token is a bearer secret: whoever holds the agent's gateway configuration can act as it |
| A payment tool moves money beyond what the user consented to | declared payment tools are authorized by AgentAuth against the consent before they run; denied, stepped-up and unanswered payments are refused or held; the gateway holds the delegation token | implemented, tested against a stand-in and the AgentAuth API; protects only tools declared with `fabric payments add` and called through the proxy; amounts are read from declared arguments, so a wrong declaration authorizes the wrong amount |
| Evidence edited, removed or reordered after the fact | hash-chained records; exported packs signed with Ed25519 and hash every file | implemented, tested; a writer to Fabric's data directory can rewrite the whole chain before any head or pack has been shared |

## Out of scope

A compromised OS or administrator; an agent intentionally deleting the store with the user's
privileges; changes outside the tracked project (databases, cloud resources, global packages) —
these can at most be reported, not undone; network filesystems.
