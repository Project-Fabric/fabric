THE COSIGNA ARCHITECTURE

From intent
to a verified outcome.

A constrained planner, an explicit authority boundary, and a durable transaction lifecycle. Each has a distinct job.

The transaction path.

01

Authenticate and scope

Derive ownership from the caller’s credential. Bind a registered agent to a budget, plan/execute permissions, expiry, and revocation state.

02

Propose a merchant-backed quote

The planner chooses an offer and quantity, or asks for clarification. Prices, currency, seller, terms, and revision come from the configured catalog.

03

Approve and reserve

The owner reviews the exact quote. Approval checks current limits and atomically reserves the allowance so concurrent tasks cannot consume the same balance.

04

Claim before execution

Recheck the approval, scope, quote, budget, and hold. Commit a stable attempt identifier before the connector performs an external write.

05

Verify the result

Match the receipt to the attempt, quote digest, amount, and currency. Confirmed acceptance settles the hold; a definite rejection releases it.

06

Reconcile uncertainty

A lost response stays unknown. Look up the original attempt without creating a replacement purchase. An absent lookup result is not proof of failure.

Where authority belongs.

Requests, transcripts, model output, and merchant text are inputs. They cannot create an owner’s approval, expand a budget, choose a credential destination, or declare payment success.

Provider credentials stay in the restricted execution path. The model receives the context needed to propose a choice, rather than a payment key or an owner credential.

Revocation stops new execution claims. An external operation already claimed may still finish and must be reconciled. Payment, merchant acceptance, and pickup readiness remain distinct outcomes.

A durable worker, with a deliberate pause.

The local API and worker share the transaction ledger. Only explicitly enrolled tasks are scheduled. The worker polls for committed approval, checks agent permissions again, and advances one operation at a time.

Failed or interrupted inference pauses for review. Unknown attempts use bounded lookup backoff and retain their holds. An operator can pause or resume scheduling, but scheduling itself never creates spending authority.

Apache Airflow runs a separate fixture verification pipeline. It tests the system; it does not authorize or schedule customer purchases.

One product, a staged code merge.

The existing tool gateway calls the consent service for authorization. The purchase engine currently uses its own budget-and-approval ledger. These paths are being aligned behind one authoritative permission contract.

The staged consolidation preserves existing commands, API contracts, and stored transaction records. A visual rebrand does not merge financial ledgers or establish production identity.

What comes before a live pilot.

  • Production owner and agent identity, with verified approval proof.
  • Signed, short-lived, single-use permits bound to the exact transaction and execution attempt.
  • One authoritative authorization path across the service and transaction engine.
  • A supported merchant and payment connector, including additional authentication and verified recovery.
  • Operating controls, monitoring, backup recovery, and independent security review.

The current server is a private development interface. Passing fixture tests does not establish universal exactly-once payments, protection against a compromised operating-system account, or recovery from every provider failure.
