The Northwind refund comparison.

Stripe test mode · 21 October 2026

Agents processed the same ten support tickets in two separate test worlds: one without payment authorization controls, and one with scoped authority enforced before a write.

The synthetic company had actual Stripe test-mode payments. Refunds were read back from Stripe and compared with the expected outcome.

Result, USDWithout controlsWith controls
Expected refunds$182.98$182.98
Actual refunds$710.98$182.98
Excess refunds$528.00$0.00
Incorrectly refunded orders20
Agent cost for that run$1.53$1.51

The guarded run refused a refund beyond the remaining consent and a refund requested by an agent with no spending authority.

One run per world, one model, and one authored scenario set. The unguarded agents were not told the budget. This comparison does not establish statistical superiority, production fraud prevention, or future savings.

Recovery after real process termination.

Four fixture regressions terminate a real child process at fixed lifecycle boundaries, reopen the store, and check the resulting attempt and budget state.

Termination pointChecked recovery
During planningPause for review; no automatic inference replay.
After submission claimPreserve the attempt and budget hold; no replacement submission.
After fixture acceptanceRecover one accepted order through lookup, even after budget revocation.
After recorded confirmationPreserve the confirmed attempt and settled balance after restart.

These are controlled fixture boundaries. They do not establish physical power-loss, full-disk, arbitrary network-partition, or every live-processor recovery behavior.

A repeatable local verification pipeline.

The optional Apache Airflow batch runs crash recovery, permission and budget regressions, replay and scope checks, HTTP boundaries, planner-output checks, and a two-process API/worker restart flow.

A final task validates every suite’s report. An isolated negative test replaced the planner test executable with an exit-code-7 fixture; the DAG returned failure and wrote a failed summary.

docker compose -f testbeds/pipeline-lab/compose.yaml run --build --rm verify

Run from the project checkout with Docker Desktop using Linux containers. The runtime uses temporary synthetic stores and its own loopback network. No model API call or real payment is involved.

The next questions to answer.

  • Do budget-conservation invariants hold over generated sequences of concurrent actions?
  • How does each processor behave after delayed webhooks or an expired idempotency window?
  • How do we recover when payment succeeds but merchant order creation fails?
  • Does a hosted planner preserve intent under ambiguity and malicious merchant content?
  • Can a partner adopt one narrow workflow with measurable operational benefit?

Test payments are evidence of a workflow, not customer traction or revenue. Verification durations are not customer transaction-latency benchmarks.
